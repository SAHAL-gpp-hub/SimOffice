ABSTRACT

Cybersecurity and software debugging are predominantly taught in academic institutions through static, isolated exercises such as sanitized code snippets, individual command-line challenges, or learning management system (LMS) worksheets. While these methods test individual syntax familiarity, they fail to simulate the collaborative, spatial, and organizational realities of professional incident response, where engineers must triage ambiguous symptoms, coordinate across specialized roles, and diagnose defects under time constraints.

SimOffice is a browser-based, multiplayer 3D virtual company simulation developed to transform collaborative debugging and secure-coding education into an embodied, team-oriented experience. In SimOffice, a teacher acts as an engineering director who configures a live session, selects a software project scenario and difficulty tier, and plants a curated defect into a real, runnable codebase. Students join the session via a lightweight class-scoped identity, enter the headquarters through an architectural 3D exterior ([3D/Entry]), control physics-driven stylized 3D avatars in a shared office building ([3D/HUD]), and sit at in-world workstations ([Hybrid]) to inspect, edit, test, and verify their team's slice of the codebase in real time.

The Phase 0 Pilot Edition of SimOffice is built using Babylon.js 8.x and React 19 (TypeScript + Vite + Zustand) on the client, a unified Node.js 24 LTS + NestJS + Colyseus 0.17.x application server for RESTful APIs and real-time WebSocket room synchronization, PostgreSQL 17.x as the relational system of record, and Valkey 8.x for presence and rate-limiting. The entire pilot stack is containerized via Docker Compose behind an Nginx reverse proxy to operate on a single low-cost Virtual Private Server (VPS) or existing campus lab hardware at $0–$10/month.

The core security innovation of SimOffice is its Trust-Zone Sandbox Architecture. Because executing untrusted student code and grading it in a classroom environment presents severe tampering and denial-of-service risks, SimOffice implements an "Injection-Over-Mount" verification model behind a unified SandboxProvider interface (supporting both gVisor runsc via a narrow-privilege sandbox-orchestrator service and E2B Firecracker microVMs). The grading verification harness never exists inside the student-writable /workspace filesystem; instead, it is injected transiently by the server into an ephemeral, isolated execution context against a point-in-time snapshot of the student's code. Strict per-environment resource ceilings (1 vCPU, 512 MB RAM, and a 30-second per-check wall-clock timeout) protect shared host infrastructure. Privacy-by-design is enforced through a two-tier identity model where students use credential-free, class-scoped RosterEntry records with human-friendly passcodes (e.g., WOLF-42) and automated in-place SQL anonymization jobs.

CHAPTER 1 — INTRODUCTION

1.1 INTRODUCTION

Software engineering and cybersecurity in the modern industry are fundamentally collaborative, spatial, and system-oriented disciplines. When a production outage, logic defect, or security incident occurs inside a technology company, engineers rarely solve it in complete isolation. Instead, they triage user-reported symptoms, examine logs, communicate across specialized organizational departments (Frontend, Backend, DevOps, and Quality Assurance), gather around shared monitors, and verify patches against live environments under time pressure.

Despite this reality, computer science and information technology education in polytechnic colleges and universities continues to rely heavily on static, solitary exercises. Students are typically presented with a pre-isolated snippet of broken code or an individual command-line challenge, given no teammates to coordinate with, and graded via a binary pass/fail script.

SimOffice addresses this pedagogical gap by introducing a browser-based, multiplayer 3D simulation that recreates the experience of working inside a real software company (PRD v3.1 §1). In SimOffice, students control a physics-driven, stylized 3D character who walks, jumps, and interacts within a virtual corporate headquarters. A teacher acts as the company's Engineering Director: opening a live session, selecting a software project scenario and difficulty tier, and injecting a deliberate defect into a real, runnable codebase. Students join department teams, read symptom-only mission briefings from in-world notice boards, sit down at physical 3D workstations to open their department's code slice via a diegetic monitor overlay, and collaborate in real time to diagnose, patch, and verify the fix inside a kernel-isolated execution sandbox.

1.2 BACKGROUND OF TECHNICAL & SECURITY EDUCATION

In technical diploma and degree programs—such as the Diploma in IT Engineering at Government Polytechnic Palanpur—practical laboratory sessions are the primary venue where students transition from theoretical concepts to applied software development. However, instructors running debugging or cybersecurity labs face three persistent structural barriers: (1) Lack of Organizational Context (students are handed the exact file rather than triaging a customer symptom), (2) Absence of Visible Collaboration (teamwork is invisible on flat screens), and (3) The Sandbox Security & Cost Dilemma (running untrusted student code risks server starvation or test-file tampering, while commercial multi-node cloud sandboxes cost $400–$1,300+/month). SimOffice resolves all three barriers simultaneously within a $0–$10/month single-VPS footprint (TSSD v2.1 §1, §7).

1.3 PROBLEM STATEMENT

  • Isolated, Non-Collaborative Exercises: Standard coding platforms evaluate students individually on sanitized snippets, failing to teach cross-role communication, incident triage, or shared ownership.
  • No Spatial or Social Presence: Flat web tools and LMS worksheets lack a sense of place. Students cannot see teammates working beside them or experience the social momentum of a shared team room.
  • High Teacher Setup Overhead & Low Observability: Instructors lack turnkey tools to spin up a controlled "live incident" across a class section, prevent repeated incidents across sections, and monitor live team progress or drop targeted hints.
  • Vulnerability to Verification Tampering: In conventional client-accessible coding environments, students can inspect, delete, or hardcode return values into the grading test script to fake a "pass" without fixing the underlying defect (PRD §8.5).
  • Resource Starvation on Shared Lab Infrastructure: Arbitrary student code executed during debugging exercises frequently contains runaway loops, memory leaks, or fork bombs that can crash a shared college server if per-team CPU, memory, and wall-clock ceilings are not strictly enforced (PRD §8.6).
  • Student Privacy & Account Friction: Requiring students to register with personal emails, real names, or third-party Single Sign-On (SSO) accounts creates compliance hurdles (COPPA/FERPA/GDPR-K) and wastes lab time (PRD §15.1, §16.6).

3.3 TRUST-ZONE & SANDBOX ARCHITECTURE ("INJECTION-OVER-MOUNT")

To prevent students from passing verification by deleting, reading, or rewriting the grading test file (PRD §8.5), SimOffice implements the "Injection-Over-Mount" principle (SAD §7.2, SSD §3.1). The verification harness never exists in the student-writable /workspace path. Instead, as resolved in TDD v1.1 (§6.1–6.2):

  • In E2BProvider: runVerification snapshots /workspace and opens a second, separate E2B Firecracker sandbox session (never an in-session exec that shares filesystem handles), copies the snapshot and harness in, executes under a 30s timeout, and destroys the session in try/finally.
  • In GVisorProvider: sandbox-orchestrator snapshots the student's /workspace volume and launches a second, short-lived runsc container with the snapshot bind-mounted read-only and the harness copied in fresh, destroying the container immediately afterward.

4.1 TWO-TIER AUTHENTICATION & ROSTER PASSCODE MODULE

4.3 REAL-TIME MULTIPLAYER & DESK CONFLICT MODULE

Each team connects to a dedicated Colyseus room (`team-${teamId}`). Because all message handlers in a Colyseus room execute synchronously on a single Node.js event-loop turn per tick, handleSitAtDesk (TDD §5) performs an atomic check-then-set against DeskRegistry.occupiedDesks. The first valid interaction wins; a simultaneous second request receives { error: "DESK_OCCUPIED", nearestFreeDeskId }. If a seated student's connection drops unexpectedly (onLeave(consented = false)), PlayerState.connected flips to false ("Stepped Away") without freeing their desk, allowing seamless reconnection.

4.4 WORKSTATION, VERIFICATION & NON-PUNITIVE DEBRIEF MODULES

  • Sequential Streaming Verification (API Spec §7.5, TDD §3.4): Loops sequentially over the variant's verification_checks (preventing self-contention against the 1 vCPU / 512 MB ceiling), broadcasts each check's result live over WebSockets as soon as it finishes, and derives outcome_state = 'resolved' strictly when all full_fix checks pass.
  • Teacher Live Dashboard & Non-Punitive Debrief (API Spec §8–§9, UIUXD §8): Combines live Colyseus room presence with team_debrief_summary metrics. // 1. Scenario/Variant Selection with No-Repeat Check (TDD §3.1, PRD §11.5.3)
export async function resolveScenarioVariant(
  repo: ScenarioVariantRepository,
  classId: string,
  input:
    | { mode: 'explicit'; scenarioVariantId: string }
    | { mode: 'random'; scenarioId: string; difficulty: Difficulty; category: Category },
): Promise<ScenarioVariant> {
  if (input.mode === 'explicit') {
    const variant = await repo.findExplicit(input.scenarioVariantId);
    if (!variant) throw new Error('NOT_FOUND');
    return variant;
  }
  const [candidates, usedIds] = await Promise.all([
    repo.findCandidates(input.scenarioId, input.difficulty, input.category),
    repo.findUsedVariantIds(classId), // Queries `sessions` directly (DBD §16 item 6)
  ]);
  const eligible = candidates.filter((c) => !usedIds.has(c.id));
  if (eligible.length === 0) throw new NoEligibleVariantError();
  return eligible[Math.floor(Math.random() * eligible.length)];
}

// 2. Sequential Verification Submission with 30s Per-Check Timeout (TDD §3.4)
export async function submitVerification(
  provider: SandboxProvider,
  checkRepo: VerificationCheckRepository,
  runWriter: VerificationRunWriter,
  outcomeWriter: TeamOutcomeWriter,
  broadcaster: RoomBroadcaster,
  env: EnvironmentRef,
  teamId: string,
  scenarioVariantId: string,
  triggeredByRosterEntryId: string,
): Promise<VerificationRunRecord[]> {
  const checks = await checkRepo.findByScenarioVariant(scenarioVariantId);
  const runs: VerificationRunRecord[] = [];
  for (const check of checks) {
    const timeout = new Promise<never>((_, reject) =>
      setTimeout(() => reject(new Error('VERIFICATION_TIMEOUT')), 30000)
    );
    const result = await Promise.race([
      provider.runVerification(env, check.harnessRef),
      timeout
    ]);
    const run = await runWriter.insert({
      teamId,
      verificationCheckId: check.id,
      triggeredByRosterEntryId,
      result: result.result
    });
    broadcaster.broadcastVerificationResult(teamId, run, check.checkType);
    runs.push(run);
  }
  const outcome = deriveOutcomeState(checks, runs);
  await outcomeWriter.setOutcomeState(teamId, outcome);
  return runs;
}

// 3. Server-Side Contribution Event Debounce Buffer (TDD §10 — 4s debounce / 8s maxWait)
export class ContributionEventBuffer {
  private pending = new Map<string, PendingEdit>();
  private readonly maxWait = 8000;
  constructor(private readonly writer: ContributionEventWriter) {}

  recordEdit(rosterEntryId: string, environmentInstanceId: string, filePath: string): void {
    const key = `${rosterEntryId}:${filePath}`;
    const existing = this.pending.get(key);
    const now = Date.now();
    const firstActivity = existing ? existing.firstActivity : now;
    if (existing) {
      clearTimeout(existing.timer);
      if (now - firstActivity >= this.maxWait) {
        this.pending.delete(key);
        void this.writer.insertCodeEditEvent(rosterEntryId, environmentInstanceId, filePath);
        return;
      }
    }
    const timer = setTimeout(() => {
      this.pending.delete(key);
      void this.writer.insertCodeEditEvent(rosterEntryId, environmentInstanceId, filePath);
    }, 4000);
    this.pending.set(key, { rosterEntryId, environmentInstanceId, filePath, timer, firstActivity });
  }
}

The Phase 0 implementation demonstrates that decoupling room creation (`POST /sessions`) from sandbox provisioning (`POST /sessions/{id}/start`) eliminates classroom startup bottlenecks: students can join the 3D lobby immediately while expensive container provisioning happens only when the teacher starts the clock. -- DEBRIEF VIEWS (DBD §10 — Pre-aggregated CTEs preventing fan-out)
CREATE OR REPLACE VIEW team_debrief_summary AS
WITH scenario_checks AS (
    SELECT s.id AS session_id,
           COUNT(*) FILTER (WHERE vc.check_type = 'full_fix') AS total_full_fix,
           COUNT(*) FILTER (WHERE vc.check_type = 'diagnostic') AS total_diagnostic
    FROM sessions s
    JOIN scenario_variants sv ON sv.id = s.scenario_variant_id
    JOIN verification_checks vc ON vc.scenario_variant_id = sv.id
    GROUP BY s.id
)
SELECT t.id AS team_id, t.session_id, t.department_id, d.display_name AS department_name,
       t.label, t.outcome_state,
       COUNT(DISTINCT vc.id) FILTER (WHERE vr.result = 'pass' AND vc.check_type = 'full_fix') AS full_fix_checks_passed,
       sc.total_full_fix AS full_fix_checks_total,
       COUNT(DISTINCT vc.id) FILTER (WHERE vr.result = 'pass' AND vc.check_type = 'diagnostic') AS diagnostic_checks_passed,
       sc.total_diagnostic AS diagnostic_checks_total,
       MIN(vr.ran_at) FILTER (WHERE vr.result = 'pass') AS first_pass_at
FROM teams t
JOIN departments d ON d.id = t.department_id
LEFT JOIN scenario_checks sc ON sc.session_id = t.session_id
LEFT JOIN verification_runs vr ON vr.team_id = t.id
LEFT JOIN verification_checks vc ON vc.id = vr.verification_check_id
GROUP BY t.id, t.session_id, t.department_id, d.display_name, t.label, t.outcome_state, sc.total_full_fix, sc.total_diagnostic;

CREATE OR REPLACE VIEW student_contribution_summary AS
WITH event_counts AS (
    SELECT roster_entry_id, session_id, team_id,
           COUNT(*) FILTER (WHERE event_type = 'code_edit_saved') AS code_edits,
           COUNT(*) FILTER (WHERE event_type = 'chat_message_sent') AS chat_messages,
           COUNT(*) FILTER (WHERE event_type = 'ping_sent') AS pings_sent,
           COUNT(*) FILTER (WHERE event_type = 'emote_used') AS emotes_used
    FROM contribution_events WHERE roster_entry_id IS NOT NULL
    GROUP BY roster_entry_id, session_id, team_id
),
verification_counts AS (
    SELECT triggered_by_roster_entry_id AS roster_entry_id, team_id,
           COUNT(*) FILTER (WHERE result = 'pass') AS verifications_triggered_pass
    FROM verification_runs WHERE triggered_by_roster_entry_id IS NOT NULL
    GROUP BY triggered_by_roster_entry_id, team_id
)
SELECT re.id AS roster_entry_id, re.display_name, t.session_id, tm.team_id,
       COALESCE(ec.code_edits, 0) AS code_edits, COALESCE(ec.chat_messages, 0) AS chat_messages,
       COALESCE(ec.pings_sent, 0) AS pings_sent, COALESCE(ec.emotes_used, 0) AS emotes_used,
       COALESCE(vc.verifications_triggered_pass, 0) AS verifications_triggered_pass
FROM team_memberships tm
JOIN roster_entries re ON re.id = tm.roster_entry_id
JOIN teams t ON t.id = tm.team_id
LEFT JOIN event_counts ec ON ec.roster_entry_id = tm.roster_entry_id AND ec.team_id = tm.team_id
LEFT JOIN verification_counts vc ON vc.roster_entry_id = tm.roster_entry_id AND vc.team_id = tm.team_id;

-- ANONYMIZATION FUNCTIONS (DBD §8)
CREATE OR REPLACE FUNCTION anonymize_expired_contribution_events(retention_days INT DEFAULT 180)
RETURNS INT AS $$
DECLARE affected INT;
BEGIN
    UPDATE contribution_events SET roster_entry_id = NULL
     WHERE roster_entry_id IS NOT NULL AND occurred_at < now() - make_interval(days => retention_days);
    GET DIAGNOSTICS affected = ROW_COUNT;
    RETURN affected;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE FUNCTION anonymize_roster_entry(target_roster_entry_id UUID)
RETURNS VOID AS $$
BEGIN
    UPDATE roster_entries
       SET display_name = 'Deleted Student', roster_passcode_hash = 'invalidated',
           is_anonymized = true, anonymized_at = now()
     WHERE id = target_roster_entry_id;
    UPDATE contribution_events SET roster_entry_id = NULL WHERE roster_entry_id = target_roster_entry_id;
    UPDATE verification_runs SET triggered_by_roster_entry_id = NULL WHERE triggered_by_roster_entry_id = target_roster_entry_id;
END;
$$ LANGUAGE plpgsql;

APPENDIX C — TROUBLESHOOTING GUIDE

  1. 409 ENVIRONMENT_NOT_READY when clicking a workstation: The session is still in the created (Lobby) or provisioning phase (API Spec §5.1, §7.1). The teacher must click Start Session on SCR-05 and wait for status to become active.
  2. 401 INVALID_ROSTER_PASSCODE on student join: The entered passcode (e.g., WOLF-42) does not match any roster entry in this class. Check spelling, or leave the field blank to create a fresh roster entry (API Spec §3.2).
  3. 409 SESSION_ROSTER_FULL on student join: Reached max_roster_size. Returning students reconnecting with their rosterPasscode are exempt from this cap; ensure the student enters their passcode rather than leaving it blank.
  4. 502 PROVISIONING_FAILED on session start: Check docker compose logs sandbox-orchestrator. Confirm /var/run/docker.sock is mounted and runsc is registered in /etc/docker/daemon.json (or verify E2B_API_KEY if using E2B).
  5. TypeScript decorator errors on Colyseus @type() annotations: Ensure "experimentalDecorators": true and "emitDecoratorMetadata": true are set in server/tsconfig.json (TDD §11 item 1).
  6. 3D Exterior (SCR-00) shows static image fallback: Browser WebGL is disabled; SimOffice's automatic webglUnavailable fallback (TDD §9.1) activated cleanly. Enable hardware acceleration in Chrome settings to restore full 3D.

APPENDIX F — GLOSSARY OF TERMS

  • Diegetic Overlay: UI anchored to an in-world 3D object (such as the workstation monitor in SCR-14) rather than a browser modal popup (SAD §12).
  • Ephemeral Verification Context: A fresh E2B session or fresh runsc container created solely for a single verification run and destroyed immediately afterward (TDD §6).
  • Injection-Over-Mount: Keeping the verification harness outside /workspace and injecting it transiently into an ephemeral execution context against a workspace snapshot (SAD §7.2, SSD §3.1).
  • Production Seam: An architectural boundary designed so single-VPS pilot components can scale to multi-institution cloud infrastructure without code rewrites (TSSD §9, SAD §17).
  • Resource Ceiling: Enforced 1 vCPU, 512 MB RAM, and 30s per-check timeout protecting shared host infrastructure (PRD §8.6, SSD §4).
