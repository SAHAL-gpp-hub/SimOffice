## ABSTRACT

Cybersecurity and software debugging are predominantly taught in academic institutions through static, isolated exercises such as sanitized code snippets, individual command-line challenges, or learning management system (LMS) worksheets. While these methods test individual syntax familiarity, they fail to simulate the collaborative, spatial, and organizational realities of professional incident response, where engineers must triage ambiguous symptoms, coordinate across roles, and diagnose defects under time constraints.

**SimOffice** is a browser-based, multiplayer 3D virtual company simulation developed to transform collaborative debugging and secure-coding education into an embodied, team-oriented experience. In SimOffice, a teacher acts as an engineering director who configures a live session, selects a software project scenario and difficulty tier, and plants a curated defect (such as a logic bug, security vulnerability, or misconfiguration) into a real, runnable codebase. Students join the session via a lightweight class-scoped identity, enter the headquarters through an architectural 3D exterior (`[3D/Entry]`), control physics-driven stylized 3D avatars in a shared office building (`[3D/HUD]`), and sit at in-world workstations (`[Hybrid]`) to inspect, edit, test, and verify their team's slice of the codebase in real time.

The Phase 0 Pilot Edition of SimOffice is engineered using **Babylon.js 8.x** and **React 19 (TypeScript + Vite)** on the client, a unified **Node.js 24 LTS + NestJS + Colyseus 0.17.x** application server for RESTful APIs and real-time WebSocket room synchronization, **PostgreSQL 17.x** as the relational system of record, and **Valkey 8.x** for presence and rate-limiting. The entire pilot stack is containerized via **Docker Compose** behind an **Nginx** reverse proxy to operate on a single low-cost Virtual Private Server (VPS) or existing campus lab hardware at $0–$10/month without sacrificing security.

The centerpiece of SimOffice's engineering is its **Trust-Zone Sandbox Architecture**. Because executing arbitrary student-authored code and grading it in a classroom environment presents severe tampering and denial-of-service risks, SimOffice implements an **"Injection-Over-Mount"** verification model behind a unified `SandboxProvider` interface (supporting both **gVisor `runsc`** via a narrow-privilege `sandbox-orchestrator` service and **E2B Firecracker microVMs**). The grading verification harness never exists inside the student-writable `/workspace` filesystem; instead, it is injected transiently by the server into an ephemeral, isolated execution context against a point-in-time snapshot of the student's code. Furthermore, strict per-environment resource ceilings (**1 vCPU, 512 MB RAM, and a 30-second per-check wall-clock timeout**) protect shared host infrastructure from infinite loops or fork bombs. Privacy-by-design is enforced through a two-tier identity model where students use credential-free, class-scoped `RosterEntry` records with human-friendly passcodes (e.g., `WOLF-42`) and automated in-place anonymization jobs.

**Keywords:** SimOffice, 3D Collaborative Learning, Babylon.js, Colyseus Multiplayer, NestJS, gVisor Sandbox, Firecracker MicroVM, Injection-Over-Mount, Tamper-Resistant Verification, Cybersecurity Education, Diegetic UI, Privacy-by-Design.

# CHAPTER 1 — INTRODUCTION

## 1.1 INTRODUCTION

Software engineering and cybersecurity in the modern industry are fundamentally collaborative, spatial, and system-oriented disciplines. When a production outage, logic defect, or security incident occurs inside a technology company, engineers rarely solve it in complete isolation. Instead, they triage user-reported symptoms, examine logs, communicate across specialized organizational departments (Frontend, Backend, DevOps, and Quality Assurance), gather around shared monitors, and verify patches against live environments under time pressure.

Despite this reality, computer science and information technology education in polytechnic colleges and universities continues to rely heavily on static, solitary exercises. Students are typically presented with a pre-isolated snippet of broken code or an individual command-line challenge, given no teammates to coordinate with, and graded via a binary pass/fail script.

**SimOffice** addresses this pedagogical gap by introducing a browser-based, multiplayer 3D simulation that recreates the experience of working inside a real software company (PRD v3.1 §1). In SimOffice, students control a physics-driven, stylized 3D character who walks, jumps, and interacts within a virtual corporate headquarters. A teacher acts as the company's Engineering Director: opening a live session, selecting a software project scenario and difficulty tier, and injecting a deliberate defect into a real, runnable codebase. Students join department teams, read symptom-only mission briefings from in-world notice boards, sit down at physical 3D workstations to open their department's code slice via a diegetic monitor overlay, and collaborate in real time to diagnose, patch, and verify the fix inside a kernel-isolated execution sandbox.

## 1.2 BACKGROUND OF TECHNICAL & SECURITY EDUCATION

In technical diploma and degree programs—such as the Diploma in IT Engineering at Government Polytechnic Palanpur—practical laboratory sessions are the primary venue where students transition from theoretical concepts to applied software development. However, instructors running debugging or cybersecurity labs face three persistent structural barriers:

1. **Lack of Organizational Context:** Traditional lab assignments hand the student the exact file containing the bug. Students rarely practice *triage*—translating a vague customer symptom (e.g., *"Customers report their payment sometimes fails silently"*) into a root-cause hypothesis across multiple service files.
2. **Absence of Visible Collaboration:** When students work on individual web forms or local IDEs, teamwork is invisible. Instructors cannot easily see from across the lab who is actively investigating, who is disconnected, or how a team is dividing its diagnostic workload.
3. **The Sandbox Security & Cost Dilemma:** Giving students a real, runnable backend service to edit and execute in the browser introduces severe infrastructure risks. Students may accidentally write infinite loops that starve the server, or curious students may attempt to "game" the grading system by deleting or modifying the unit test that checks their work. Conversely, commercial cloud sandboxes and multi-tenant Kubernetes clusters often cost hundreds of dollars per month, placing them out of reach for self-funded academic deployments.

SimOffice was conceived and engineered specifically to resolve all three barriers simultaneously: combining a playful, *Fall Guys*-inspired 3D social world with a rigorous, tamper-resistant, near-zero-cost ($0–$10/month) kernel-isolated code execution backend (TSSD v2.1 §1, §7).

## 1.3 PROBLEM STATEMENT

The existing approaches to teaching collaborative software debugging and cybersecurity suffer from the following core problems (PRD v3.1 §2, SSD v1.0 §2):

* **Isolated, Non-Collaborative Exercises:** Standard coding platforms evaluate students individually on sanitized snippets, failing to teach cross-role communication, incident triage, or shared ownership.
* **No Spatial or Social Presence:** Flat web tools and LMS worksheets lack a sense of place. Students cannot see teammates working beside them, gather around a desk to inspect a suspicious function, or experience the social momentum of a shared team room.
* **High Teacher Setup Overhead & Low Observability:** Instructors lack turnkey tools to spin up a controlled "live incident" across a class section, inject varied defects so sections cannot copy answers, and monitor live team progress or drop targeted hints without micromanaging.
* **Vulnerability to Verification Tampering:** In conventional client-accessible coding environments, students can inspect, delete, or hardcode return values into the grading test script to fake a "pass" without fixing the underlying defect (PRD §8.5).
* **Resource Starvation on Shared Lab Infrastructure:** Arbitrary student code executed during debugging exercises frequently contains runaway `while(true)` loops, memory leaks, or fork bombs that can crash a shared college server if per-team CPU, memory, and wall-clock ceilings are not strictly enforced (PRD §8.6).
* **Student Privacy & Account Friction:** Requiring students to register with personal emails, real names, or third-party Single Sign-On (SSO) accounts creates compliance hurdles (COPPA/FERPA/GDPR-K) and wastes valuable lab time during onboarding (PRD §15.1, §16.6).

## 1.4 OBJECTIVES OF THE PROJECT

### 1.4.1 Primary Objectives

1. **Build an Embodied 3D Multiplayer Workplace:** Develop a browser-based 3D simulation using Babylon.js and Colyseus where students navigate a virtual company building (starting with the architectural Building Exterior `SCR-00` and Backend Engine Room in Phase 0) with real-time avatar synchronization.
2. **Implement a Diegetic In-World Workstation Loop:** Enable students to physically sit at an in-world desk to open a scoped, auto-saving code editor (`[Hybrid]` layer) connected to a live, isolated team codebase without breaking immersion via browser popups (PRD §8.2, §16.1).
3. **Enforce "Injection-Over-Mount" Verification Tamper Resistance:** Architect a strict trust-zone separation where the grading verification harness never exists in the student-writable `/workspace` path, but is injected transiently by the server into an ephemeral execution context against a snapshot of the student's code (PRD §8.5, SAD §7.2, SSD §3).
4. **Guarantee Kernel-Level Isolation & Resource Ceilings:** Abstract code execution behind a `SandboxProvider` interface supporting gVisor (`runsc`) and E2B Firecracker sandboxes, enforcing per-environment ceilings of **1 vCPU, 512 MB RAM, and a 30-second check timeout** (PRD §8.6, SAD §7.4).
5. **Deliver a Privacy-Preserving Two-Tier Identity Model:** Provide credentialed accounts for teachers while allowing students to join via 6-character session codes and persistent, class-scoped `RosterEntry` passcodes (e.g., `WOLF-42`), collecting zero unnecessary PII and supporting automated data anonymization (PRD §15.1, §15.5, API Spec §3.2).
6. **Provide Non-Punitive Debriefing & Teacher Oversight:** Equip teachers with a live dashboard (tracking seated status, check progress, hints, and announcements) and a post-session debrief screen that distinguishes partial diagnostic progress from total failure and includes a deliberate teacher-triggered **"Reveal Fix"** control (PRD §12.10, §13.3, UIUXD §8).

### 1.4.2 Secondary Objectives

7. **Optimize for Single-College Pilot Economics:** Package the entire backend, database, cache, reverse proxy, and sandbox orchestrator via Docker Compose to run on a single $0–$10/month VPS or campus lab machine while preserving clean architectural seams for future Kubernetes scaling (TSSD v2.1 §5, SAD §17).
8. **Ensure Classroom Session Resilience:** Handle late student joins, mid-session network drops ("stepped away" seat preservation), simultaneous desk-interaction conflicts, early teacher session termination, and 20-minute abandoned-session auto-teardown (PRD §12.13, SAD §8.3).
9. **Support Accessibility & Baseline School Hardware:** Enforce a unified keyboard-reachable input-mapping layer, visual/captioned equivalents for all audio cues, `prefers-reduced-motion` camera fallbacks, and WebGL-unavailable 2D fallbacks suitable for Chromebook-class devices (PRD §9.6, §16.2, §16.5, UIUXD §10).

## 1.6 MOTIVATION

The motivation for SimOffice stems from both educational observation and systems-engineering challenge. In standard software development laboratories, students frequently treat debugging as a solitary, frustrating chore—staring at error messages alone until time expires. Yet those same students enthusiastically collaborate, communicate, and strategize when playing multiplayer games with spatial awareness.

From an engineering perspective, building SimOffice provided an opportunity to solve hard, real-world distributed systems problems that go far beyond a standard CRUD application: combining 3D WebGL rendering (Babylon.js) with authoritative state synchronization (Colyseus), designing a zero-trust code verification pipeline ("injection-over-mount"), isolating untrusted student processes with kernel-level container runtimes (`runsc`), and engineering a complete 15-document specification suite that bridges product vision to verifiable code.

# CHAPTER 2 — SYSTEM OVERVIEW & REQUIREMENT ANALYSIS

## 2.1 EXISTING CLASSROOM & SANDBOX SYSTEMS

Currently, educational institutions teach programming, debugging, and cybersecurity through three disconnected categories of tools:

1. **Learning Management Systems (LMS) & Static Worksheets:** Platforms such as Moodle, Google Classroom, or paper lab manuals distribute problem descriptions and code snippets. Students edit code locally and upload files or screenshots for manual grading by faculty.
2. **Algorithmic & Competitive Coding Platforms:** Tools like LeetCode, HackerRank, or Codeforces provide browser-based editors and automated test runners. However, they focus on single-file algorithmic puzzles rather than multi-file application debugging, and they are strictly single-player.
3. **Browser-Based Cloud IDEs & CTF Platforms:** Platforms such as GitHub Codespaces, Replit, or traditional Capture-The-Flag (CTF) portals provide full development environments or vulnerable containers. However, cloud IDEs lack game-like spatial presence, structured incident briefings, or teacher observability dashboards, while CTF portals focus on penetration testing commands rather than collaborative software engineering triage across organizational roles.

## 2.2 LIMITATIONS OF EXISTING SYSTEMS

Table 2.1 summarizes the operational, pedagogical, and security limitations of existing classroom debugging methods:

| Issue / Limitation | Impact on Classroom Operations & Pedagogy | Severity |
| :--- | :--- | :--- |
| **Single-player, isolated workflows** | Students do not practice team triage, role division, or collaborative root-cause analysis. | High |
| **Client-accessible test harnesses** | Students in local or standard container labs can read, delete, or modify test files to fake a passing grade (PRD §8.5). | Critical |
| **No protection against runaway code on shared servers** | An accidental infinite loop or fork bomb in one student's code degrades or crashes the lab server for the entire class (PRD §8.6). | Critical |
| **Flat, non-spatial interfaces** | Zero sense of "being at work"; students cannot see who is working where or naturally huddle around a teammate's screen. | High |
| **Punitive binary grading ("PASS / FAIL")** | Teams that correctly diagnose the faulty file/function but run out of time before completing the syntax fix receive zero credit or feedback (PRD §13.3). | High |
| **Heavy account & PII requirements** | Requiring student email registration or SSO delays lab startup and triggers student data privacy compliance burdens (PRD §15.1, §16.6). | High |
| **High cloud infrastructure cost** | Multi-node Kubernetes clusters and paid cloud IDE seats cost $400–$1,300+/month, making them unviable for single-college academic pilots (TSSD §7). | Medium |
| **Lack of live teacher observability & hints** | Teachers must walk from desk to desk physically to check progress and cannot push live in-world incident updates or targeted team hints. | Medium |

*Table 2.1: Limitations of Existing Classroom & Coding Sandbox Systems*

## 2.3 PROPOSED SYSTEM: SIMOFFICE

**SimOffice** replaces disconnected worksheets and isolated coding boxes with a persistent, shared 3D virtual software company (PRD v3.1 §3, §7). Every laboratory session is structured as a live **incident run**:

1. **Arrival at the Headquarters Exterior (`SCR-00`):** When a teacher or student opens SimOffice in a standard web browser, the Babylon.js engine immediately renders the architectural 3D exterior of the SimOffice headquarters. Authentication occurs through a diegetic digital access panel integrated into the building entrance—eliminating conventional flat login pages (PRD §10.4, UIUXD `SCR-00`).
2. **Threshold Transition & Lobby Onboarding:** Upon valid login (teacher) or join-code entry (student), the entrance doors animate open and a 2-second camera fly-through carries the user across the threshold into the Lobby, where the visual style shifts to SimOffice's warm, playful, *Fall Guys*-inspired aesthetic. First-time students customize their character (`SCR-07`) and traverse a short onboarding corridor (`SCR-08`) that teaches movement and interaction without precision-timing barriers.
3. **Symptom-Only Mission Briefing (`SCR-10`):** Inside the department room (the **Backend Engine Room** in Phase 0), an in-world notice board displays the incident's user-visible symptom—never the underlying cause.
4. **Seated In-World Workstation Debugging (`SCR-14`):** Students walk up to an empty desk and sit down. Their avatar visibly occupies the seat (`SCR-11`), lighting up the monitor for all teammates to see. A position-anchored `[Hybrid]` code editor opens over the 3D monitor, exposing the team's isolated codebase slice (`/workspace`), auto-saving edits (`PUT /files/{path}`), and allowing informal checks (`run-check`).
5. **Tamper-Resistant Verification (`SCR-21`):** When the team submits their fix (`submit-verification`), `app-server` snapshots `/workspace` and injects the author-controlled verification harness into a separate, ephemeral sandbox context (`runsc` or E2B). Results stream back per check (`full_fix` and `diagnostic`), triggering in-world confirmation chimes and visual prop state changes.
6. **Non-Punitive Debrief & "Reveal Fix" (`SCR-19` / `SCR-20`):** When the session ends, both teacher and students receive structured debrief cards showing diagnostic progress, individual contribution metrics (inferred from code edits, verification triggers, chat, and pings), and an optional teacher-triggered **"Reveal Fix"** teaching moment for unresolved teams.

## 2.4 TARGET USERS AND PERSONA ANALYSIS

SimOffice is designed around four explicitly defined personas (PRD v3.1 §6, UIUXD v2.1 §4):

* **Persona 1 — "Mentor Priya" (Teacher / Instructor):** Teaches software engineering, secure coding, or systems courses. Uses the `[Shell]` workflow (`SCR-01` to `SCR-05`, `SCR-15` to `SCR-19`) to create classes, launch incident sessions, monitor live roster/check status, push hints or customer alerts, and export post-session debriefs.
* **Persona 2 — "Student Rahul" (Team Contributor):** Joins via a 6-character code (`SCR-06`), retains a persistent class-scoped identity via a lightweight passcode (`WOLF-42`), customizes an avatar (`SCR-07`), collaborates via chat (`SCR-12`) and location pings (`SCR-13`), edits code at a workstation (`SCR-14`), and receives a personal contribution debrief (`SCR-20`).
* **Persona 3 — "Content Author Dev" (Curriculum Designer):** Distinct from the classroom teacher (PRD §11.4). Authors self-contained scenario packages (`content-library/`) consisting of a `fix-baseline`, broken `issue-variants`, protected `verification` harnesses, and `manifest.yaml` metadata, validated through a two-part correctness and pedagogical review gate.
* **Persona 4 — "IT / Procurement Admin Alex" (Institutional Approver):** Evaluates SimOffice against campus hardware baselines (Chromebook/lab PC compatibility), network firewall rules (single `:443` port exposure), and student data privacy/retention compliance (PRD §15.5, §16.6).

# CHAPTER 3 — SYSTEM ARCHITECTURE & SECURITY DESIGN

## 3.1 ARCHITECTURAL GOALS AND CONSTRAINTS

The SimOffice System Architecture (SAD v1.3/v1.4) translates the requirements of PRD v3.1/v3.2 and the technology selections of TSSD v2.1 into a cohesive, security-hardened topology. Six primary architectural constraints govern the design (SAD §2):

1. **Coarse-Grained Single-Host Pilot Deployment:** To achieve the $0–$10/month pilot cost target, the REST API and the Colyseus real-time multiplayer server execute inside a **single Node.js process (`app-server`)** orchestrated via Docker Compose rather than a multi-cluster microservice sprawl.
2. **Strict Kernel-Level Sandbox Isolation:** Every team's code execution environment is isolated at the OS/kernel boundary behind a provider-agnostic `SandboxProvider` interface.
3. **"Injection-Over-Mount" Verification Trust Zone:** The verification harness is never mounted inside the student-writable `/workspace` directory; it is injected transiently into a separate execution context at verification time.
4. **Per-Environment Resource Ceilings:** Every provisioned sandbox enforces explicit CPU, memory, and wall-clock limits (`ResourceLimits`) so runaway student code cannot starve PostgreSQL, Valkey, or other teams on the shared VPS.
5. **Two-Tier Identity Separation:** Credentialed `Account` rows for teachers and credential-free, class-scoped `RosterEntry` rows for students are kept structurally separate.
6. **Unconditional Session Teardown:** Environment teardown (`torn_down`) is a mandatory terminal step across all session-end paths (normal end, early teacher end, time limit, or abandoned timeout).

## 3.4 THREE-LAYER FRONTEND ARCHITECTURE (`[3D/ENTRY]`, `[SHELL]`, `[3D/HUD]`, `[HYBRID]`)

As refined in SAD v1.4 (§12) and UIUXD v2.2 (§5), the client avoids creating and destroying multiple WebGL contexts by operating a **single Babylon.js engine lifecycle** from initial page load through session end, organized into three architectural layers plus one hybrid composition:

1. **`[3D/Entry]` Layer (Pre-Auth Building Exterior):** Rendered immediately on page load (`initEntryScene()`). Displays the modern architectural SimOffice headquarters exterior with ambient lighting. The React App Shell floats the diegetic access panel card (`SCR-00`) over the canvas (`/teacher` renders staff login `SCR-01`; `/` renders student join `SCR-06`).
2. **`[Shell]` Layer (React 19 2D App Shell):** Handles teacher workflows outside the 3D simulation (Class List `SCR-02`, Roster `SCR-03`, Session Setup `SCR-04`, Lobby Control `SCR-05`, Live Dashboard `SCR-15`, Teacher Debrief `SCR-19`) and the student's post-session personal debrief (`SCR-20`).
3. **`[3D/HUD]` Layer (Babylon.js In-World Simulation):** When authentication succeeds and the 2-second entry camera fly-through crosses the building threshold, the *existing* Babylon.js engine instance is promoted in-place via `initGameWorld()`. It renders the stylized interior, physics-driven avatars, and transparent-background HUD overlays (Contextual Prompts `SCR-09`, Notice Board `SCR-10`, Desk Indicators `SCR-11`, Chat `SCR-12`, Pings `SCR-13`).
4. **`[Hybrid]` Layer (Workstation Code Editor Overlay — `SCR-14`):** To satisfy PRD §8.2 and §16.1 ("no popup-style UI"), sitting at a desk settles the 3D camera into an over-the-shoulder view of the in-world monitor and anchors a real DOM CodeMirror editor directly to the monitor's frame. Teammates remain visible walking past in peripheral 3D view, and standing up immediately dismisses the overlay while auto-saving file state.

All pointer/mouse interactions are routed through a **single Input-Mapping Abstraction Layer** (SAD §12) that binds every action (`move`, `jump`, `sit`, `interact`, `emote`) to keyboard equivalents, making PRD §9.6's keyboard-only accessibility rule enforceable during code review.

### Fault Isolation in a Single-Process Server (SAD §14)
Because NestJS and Colyseus share one Node.js event loop, an unhandled exception inside a Colyseus room callback could theoretically crash the REST API. SimOffice prevents this via a **three-layer resilience defense** (SAD v1.3 §14):
1. **Per-Callback Try/Catch Wrapping:** Every room lifecycle method (`onJoin`, `onMessage`, `onLeave`, `onDispose`) is individually wrapped in a `try/catch` block that logs exceptions to Sentry (tagged with `session_id` and `team_id`) and gracefully degrades only that specific room.
2. **Top-Level Process Handlers:** `process.on('uncaughtException')` and `process.on('unhandledRejection')` flush error logs and trigger a clean, controlled exit rather than leaving the server in an undefined state.
3. **Process Supervision & Native Reconnection:** Container restart policies (`restart: unless-stopped` / `pm2`) immediately restart `app-server`, while Colyseus 0.17's native client reconnection automatically restores students to their room and seated workstation state.

In a classroom setting, students will predictably attempt to pass an exercise by deleting the test file, modifying assertions, or inspecting the test script to hardcode expected outputs.

### 3.6.2 The "Injection-Over-Mount" Principle
Rather than placing the verification test suite inside `/workspace` with read-only permissions (which a root escalation or container misconfiguration could bypass), SimOffice enforces **Injection-Over-Mount** (SAD §7.2, SSD §3.1):
* The verification harness **never exists** in any path resolvable by the student's `readFile` or `writeFile` API calls.
* When a student triggers `POST /teams/{teamId}/workstation/submit-verification`, `app-server` executes `runVerification(env, harnessRef)` using the 6-step flow shown in Figure 3.4:

```
+-------------------------------------------------------------------------+
|                runVerification(env, harnessRef) FLOW                    |
+-------------------------------------------------------------------------+
|  1. Snapshot the student's current /workspace filesystem from `env`.    |
|  2. Provision a brand-new, separate isolation context                   |
|     (a second E2B sandbox session OR a second `runsc` container).       |
|  3. Inject the point-in-time /workspace snapshot + the protected        |
|     author verification harness (`harnessRef`) into the new context.    |
|  4. Execute the harness under a strict 30-second wall-clock timeout     |
|     (`Promise.race`), capturing pass / fail / resource_limit_exceeded.  |
|  5. Destroy the ephemeral verification context unconditionally          |
|     (`try / finally`).                                                  |
|  6. Write the authoritative `VerificationRun` row to PostgreSQL and     |
|     broadcast `verificationResult` to the Colyseus room.                |
+-------------------------------------------------------------------------+
```
*Figure 3.4: "Injection-Over-Mount" Ephemeral Verification Execution Flow (SAD §7.2, SSD §3.4)*

### 3.6.3 Concrete Provider Implementations

| Architectural Aspect | `E2BProvider` (Cloud MicroVM Path) | `GVisorProvider` (Self-Hosted Campus/VPS Path) |
| :--- | :--- | :--- |
| **Student `/workspace`** | E2B Firecracker microVM filesystem via E2B SDK. | Bind-mounted volume inside a `runsc`-runtime Docker container. |
| **Ephemeral Verification Context** | A **second, separate E2B sandbox session** (never a scoped `exec` in the student's session, preventing shared filesystem handles). | A **second, short-lived `runsc` container** launched by `sandbox-orchestrator` mounting a read-only snapshot + injected harness. |
| **Kernel Isolation Mechanism** | AWS Firecracker microVM hardware virtualization. | Google gVisor (`runsc`) user-space application kernel intercepting syscalls. |
| **Resource Ceiling Enforcement** | E2B SDK per-sandbox vCPU/RAM config + `app-server` 30s timeout. | Docker `--cpus=1 --memory=512m` flags at container create + 30s timeout. |

### 3.7.1 Threat Actors and Defenses (SSD §2.1, §3.5)

| Threat Actor / Vector | Capability & Motivation | SimOffice Architectural Defense |
| :--- | :--- | :--- |
| **Curious Student (Tampering)** | Attempts `../../` path traversal, file deletion, or reading the grading script to fake a pass. | Path normalization + **Injection-Over-Mount**: harness does not exist in `/workspace`. Client-reported passes are ignored; only server-computed DB rows count. |

| **External Brute-Force Attacker** | Guesses teacher passwords or 6-character session join codes. | Valkey-backed sliding-window rate limiting (`429 RATE_LIMITED`: 5 req/min on login, 10 req/min on join). |

### Key Data-Modeling Decisions (SAD §6.2)
1. **Persistent Class-Scoped `ROSTER_ENTRIES`:** Unlike naive designs that create a new student row per session, `roster_entries` is scoped to `class_id` and authenticated via `roster_passcode_hash` (`WOLF-42`). This allows `appearance` (JSONB cosmetics) and multi-session history to persist across an entire semester without collecting student emails.
2. **Separation of `SCENARIOS` and `SCENARIO_VARIANTS`:** One base project (`scenarios`) supports multiple planted defects (`scenario_variants`). Before creating a session, `app-server` queries `sessions` by `(class_id, scenario_variant_id)` to enforce PRD §11.5.3's **"no repeat incident"** rule.
3. **First-Class `VERIFICATION_CHECKS`:** Splitting checks into `full_fix` and `diagnostic` rows allows `verification_runs` to record partial diagnostic credit independently of whether the team solved the entire bug.
4. **Orthogonal Session Lifecycle vs. Team Outcome:** `sessions.status` tracks infrastructure lifecycle (`created`, `provisioning`, `active`, `ended`, `debriefed`, `torn_down`) and `sessions.end_reason` records why the clock stopped (`time_limit_reached`, `teacher_ended_early`, `all_teams_resolved`, `abandoned_timeout`), while `teams.outcome_state` (`in_progress`, `resolved`, `unresolved`) tracks each team's pedagogical result independently.

## 4.1 TWO-TIER AUTHENTICATION & IDENTITY MODULE

As refined in API Spec v1.1 (§3.2), the join response always returns the student's `appearance` JSONB object and echoes back `rosterPasscode`. ## 4.2 CLASS, ROSTER & PRIVACY ANONYMIZATION MODULE

Teachers organize their courses into `classes` (`POST /api/v1/classes`, `GET /api/v1/classes`, `PATCH /api/v1/classes/{classId}`). Student rosters are not manually typed in advance by the teacher; instead, `roster_entries` populate reactively as students join their first session in that class (UIUXD `SCR-03`).

To comply with student data deletion rights (PRD §15.5, SAD §6.3, SSD §7.2), SimOffice implements **two non-destructive anonymization mechanisms** rather than hard SQL `DELETE` statements (which would break foreign keys and corrupt teammates' shared debrief histories):
1. **On-Request Student Deletion (`DELETE /api/v1/classes/{classId}/roster/{rosterEntryId}`):** Executes `anonymize_roster_entry()`, replacing `display_name` with `'Deleted Student'`, invalidating `roster_passcode_hash`, setting `is_anonymized = true`, and setting `roster_entry_id = NULL` on all historical `contribution_events` and `verification_runs`.
2. **Scheduled Age-Based Retention Sweep (`anonymize_expired_contribution_events()`):** A nightly background cron job nulls `roster_entry_id` on `contribution_events` older than the configured retention window (default 180 days), preserving aggregate team statistics while stripping individual student attribution.

A key architectural refinement in SAD v1.3 (§8.1, §11.1) and API Spec v1.1 (§5.1) decouples **Room Opening** from **Sandbox Provisioning**:
* When a teacher calls `POST /api/v1/sessions`, the server immediately creates the `sessions` row (`status = 'created'`), creates the `teams` row, and **opens the Colyseus WebSocket room**. This allows students to join the lobby (`SCR-05`), roam the 3D space, chat, and customize their avatars while waiting for the class to assemble. Workstations remain locked (`409 ENVIRONMENT_NOT_READY`).

## 4.5 IN-WORLD WORKSTATION & CODE EXECUTION MODULE

When seated at a workstation (`SCR-14`), the student interacts with their department's codebase slice via three REST endpoints scoped to their `teamId` claim (API Spec §7.1–7.4):
* **Browse File Tree (`GET /api/v1/teams/{teamId}/workstation/files`):** Returns the directory tree inside `/workspace` (e.g., `services/payment/retry.ts`).
* **Read & Auto-Save Code (`GET` & `PUT /api/v1/teams/{teamId}/workstation/files/{path}`):** Reads file content and debounces client edits to save checkpoints automatically without an explicit Save button (Principle P7). Every checkpoint logs a `code_edit_saved` event in `contribution_events`.
* **Informal Check (`POST /api/v1/teams/{teamId}/workstation/run-check`):** Executes the scenario's informal test/reproduction script inside the student's sandbox under the 30-second timeout ceiling (`SandboxProvider.runCheck`). Returns `{ result: "pass" | "fail", output }` (or `422 RESOURCE_LIMIT_EXCEEDED`), allowing iterative debugging without affecting formal grading.

## 4.6 TAMPER-RESISTANT VERIFICATION & GRADING MODULE

When the team is ready to verify their fix, a student clicks **Submit for Verification** (`POST /api/v1/teams/{teamId}/workstation/submit-verification`). Figure 4.4 illustrates the complete trust-zone sequence (SAD v1.3 §11.2, API Spec §7.5):

```
Student          Colyseus Room          app-server (NestJS)          SandboxProvider          PostgreSQL
  |                    |                         |                          |                     |
  |-- PUT /files/{p} ->|------------------------>|                          |                     |
  |                    |                         |-- writeFile(/workspace)->|                     |
  |                    |                         |-- INSERT code_edit_saved-|-------------------->|
  |                    |                         |                          |                     |
  |-- POST /submit-verification ---------------->|                          |                     |
  |                    |                         |-- SELECT Checks -------->|-------------------->|
  |                    |                         |   (full_fix + diagnostic)|                     |
  |                    |                         |                          |                     |
  |                    |                         |== [LOOP EACH CHECK] ==== |                     |
  |                    |                         |-- runVerification() ---->|                     |
  |                    |                         |   (Snapshot /workspace + |                     |
  |                    |                         |    Inject harnessRef in  |                     |
  |                    |                         |    ephemeral container)  |                     |
  |                    |                         |<-- pass/fail/limit ------|                     |
  |                    |                         |-- INSERT VerificationRun-|-------------------->|
  |                    |<-- broadcast(result) ---|                          |                     |
  |<-- Chime & Prop ---|   (Streams per check!)  |                          |                     |
  |                    |                         |== [END LOOP] =========== |                     |
```

Crucially, results **stream per check** over the Colyseus WebSocket (`verificationResult`) as soon as each check finishes rather than blocking on the slowest check (API Spec §7.5). Only a `pass` on the `full_fix` check transitions `teams.outcome_state` to `'resolved'`; passing a `diagnostic` check records partial credit (`diagnosticChecksPassed > 0`) for the debrief screen.

## 4.7 TEACHER LIVE DASHBOARD, HINTS & ANNOUNCEMENTS MODULE

During an active session, the teacher monitors the class via the Live Dashboard (`SCR-15`, `GET /api/v1/sessions/{sessionId}/dashboard`). Because NestJS and Colyseus share one process, this endpoint combines PostgreSQL verification aggregates (`fullFixChecksPassed`, `diagnosticChecksPassed`, `resourceLimitExceeded`) with in-memory Colyseus `PlayerState` data (`connected`, `seated`, `deskId`) in a single zero-latency call (API Spec §8.1).

From `SCR-15`, the teacher can:
* **Send a Targeted Team Hint (`SCR-16`, `POST /api/v1/sessions/{sessionId}/teams/{teamId}/hint`):** Broadcasts an ephemeral `hintReceived` event to a struggling team without revealing it to other teams.
* **Push a Live Incident Announcement (`SCR-17`, `POST /api/v1/sessions/{sessionId}/announcements`):** Updates the in-world Notice Board (`SCR-10`) across one or all teams with a chime and visual flash.
* **End Session (`SCR-18`, `POST /api/v1/sessions/{sessionId}/end`):** Displays a confirmation modal explicitly stating that any `in_progress` team will receive a non-punitive `unresolved` outcome, flushes `sessionEnded` over WebSockets (with a 2–3 second grace period), and tears down all sandbox environments before returning `200 OK`.

## 4.8 NON-PUNITIVE DEBRIEF & "REVEAL FIX" MODULE

At session end, SimOffice generates two distinct debrief views:
1. **Teacher Debrief (`SCR-19`, `GET /api/v1/sessions/{sessionId}/debrief`):** Backed by the `team_debrief_summary` SQL view. If a team has `outcomeState == 'unresolved'` and `diagnosticChecksPassed > 0 && fullFixChecksPassed == 0`, the UI explicitly renders *"Found the right file/area, didn't reach the full fix before time expired"* rather than a punitive "FAILED" badge (Principle P4, UIUXD §6 `SCR-19`).
2. **Teacher-Triggered "Reveal Fix" (`POST /api/v1/sessions/{sessionId}/teams/{teamId}/reveal-fix`):** Resolving the UI decision deferred in PRD §13.3 step 4 (UIUXD §8, API Spec §9.2), each unresolved team card on `SCR-19` includes a secondary **"Reveal Fix"** button with a confirmation step. Triggering this endpoint sets `revealedAt` and unlocks `fixContent` on the server so that affected students cannot inspect network traffic to see the root cause until the teacher deliberately reveals it.
3. **Student Personal Debrief (`SCR-20`, `GET /api/v1/sessions/{sessionId}/debrief/me`):** Backed by `student_contribution_summary`. Scoped strictly to `"me"` via the student's JWT (preventing ID-guessing across students), displaying `codeEdits`, `chatMessages`, `pingsSent`, `emotesUsed`, `verificationsTriggeredPass`, and—if revealed by the teacher—the conditional *"What actually caused this"* root-cause explanation.

## 5.3 SANDBOX PROVIDER INTERFACE & ORCHESTRATOR IMPLEMENTATION

Every module inside `server/` interacts with student code environments exclusively through the `SandboxProvider` TypeScript contract (SAD §7.1, SSD §3.2):

```typescript
// server/src/sandbox/sandbox-provider.interface.ts
export interface ResourceLimits {
  cpuCores: number;           // Pilot default: 1 vCPU
  memoryMb: number;           // Pilot default: 512 MB
  wallClockTimeoutMs: number; // Pilot default: 30,000 ms per check
}

export interface EnvironmentRef {
  teamId: string;
  provider: 'gvisor' | 'e2b';
  providerRef: string;
}

export interface CheckResult {
  result: 'pass' | 'fail' | 'resource_limit_exceeded';
  output: string;
}

export interface VerificationResult {
  result: 'pass' | 'fail' | 'resource_limit_exceeded';
  diagnosticDetails: Record<string, unknown>;
}

export interface SandboxProvider {
  provision(
    teamId: string,
    scenarioVariantId: string,
    limits: ResourceLimits
  ): Promise<EnvironmentRef>;

  readFile(env: EnvironmentRef, relativePath: string): Promise<string>;
  writeFile(env: EnvironmentRef, relativePath: string, content: string): Promise<void>;
  runCheck(env: EnvironmentRef): Promise<CheckResult>;
  runVerification(env: EnvironmentRef, harnessRef: string): Promise<VerificationResult>;
  teardown(env: EnvironmentRef): Promise<void>;
}
```

### Enforcing Path Traversal Protection and "Injection-Over-Mount"
When `readFile` or `writeFile` is invoked, path normalization ensures the student cannot escape `/workspace` (`path.posix.normalize` rejecting any `..` prefix). When `submitVerification` is called, `app-server` wraps the execution in a 30-second timeout race and guarantees ephemeral cleanup in a `try / finally` block:

```typescript
// Ephemeral Injection-Over-Mount Verification Pattern (SSD §3.4, §4.1)
async executeCheckWithCeiling(
  env: EnvironmentRef,
  harnessRef: string,
  timeoutMs = 30000
): Promise<VerificationResult> {
  const timeoutPromise = new Promise<VerificationResult>((resolve) =>
    setTimeout(() => resolve({
      result: 'resource_limit_exceeded',
      diagnosticDetails: { reason: `Check exceeded ${timeoutMs}ms wall-clock ceiling` }
    }), timeoutMs)
  );

  // sandbox-orchestrator snapshots /workspace, starts a fresh runsc container
  // with --cpus=1 --memory=512m --network=none, injects harnessRef, runs, and destroys in finally{}
  return Promise.race([
    this.sandboxProvider.runVerification(env, harnessRef),
    timeoutPromise,
  ]);
}
```

# CHAPTER 6 — TESTING & SECURITY VERIFICATION

## 6.1 MULTI-TIER TESTING STRATEGY

In accordance with the SimOffice Testing Plan (`TP v1.0`) and Security & Sandbox Design (`SSD v1.0` §14), verification is structured across five distinct testing tiers (TSSD v2.1 §3, §5.8):
1. **Unit & Schema Validation Testing (`Vitest`):** Tests NestJS services, passcode generation (`WOLF-42`), path-traversal sanitization, JWT guards, and database constraint logic.
2. **Security Proof-of-Concept (PoC) Verification (`SSD §14.1`):** Seven mandatory adversarial security tests verifying trust-zone tamper resistance, cross-team isolation, resource ceiling enforcement, and server-authoritative grading.
3. **End-to-End UI & API Flow Testing (`Playwright`):** Automates the `[Shell]` teacher setup (`SCR-01` to `SCR-05`), student join and character creation (`SCR-06`, `SCR-07`), dashboard hint/announcement pushes (`SCR-15` to `SCR-18`), and non-punitive debrief/reveal-fix flows (`SCR-19`, `SCR-20`).
4. **Concurrency & Rate-Limit Load Testing (`k6`):** Validates Valkey rate-limiting thresholds (`429 RATE_LIMITED`) and concurrent WebSocket room synchronization.
5. **Physical Campus Hardware Baseline Testing:** Executes the Babylon.js 3D scene directly on campus lab machines and Chromebooks to record join time, sustained FPS, and check latency (PRD §16.2, TSSD §10).

## 7.1 UI/UX DESIGN PRINCIPLES & TAXONOMY

The SimOffice user interface is governed by eight non-negotiable design principles derived from PRD v3.1/v3.2 and formalized in UIUXD v2.1/v2.2 (§3):

| Principle ID | Design Principle | Excluded Anti-Pattern (What It Rules Out) |
| :--- | :--- | :--- |
| **P1** | **Shared Object Visibility:** Object state changes are visible to everyone in the room. | Hidden menus that update state silently for only one player. |
| **P2** | **Diegetic Contextual Prompts:** In-world interactions use contextual prompts, never browser popups. | Browser-style modal dialogs inside the 3D world. |
| **P3** | **Keyboard-First Parity:** Every pointer-reachable action is keyboard-reachable via the shared input layer. | Mouse-only controls or precision-timed platforming barriers. |
| **P4** | **Non-Punitive Framing:** Partial diagnostic progress is always distinguished from total failure. | A bare "FAILED" badge anywhere in the product (`SCR-15`, `SCR-19`, `SCR-20`). |
| **P5** | **Visual/Captioned Audio Parity:** Every audio cue has a visual equivalent on the in-world object itself. | Audio-only alarms, chimes, or notifications. |
| **P6** | **Explicit Resource-Limit Outcome:** Ceiling breaches render as a defined outcome, never an infinite spinner. | Indefinite loading spinners when a student writes an infinite loop (`SCR-14`/`22`). |
| **P7** | **Automatic Progress Saving:** Code edits and cursor state save automatically on a debounce timer. | Manual "Save" buttons that a student can forget to press before standing up. |
| **P8** | **Continuous World State on Reconnect/Late Join:** Returning students see the live world as it stands. | Resetting the environment or showing a "fresh start" screen to a late joiner. |

2. **Database & Type-Safety Verification (`DBD §14`, `TDD §11`):** All 15 PostgreSQL tables, foreign-key `RESTRICT`/`SET NULL` rules, partial indexes, CTE-pre-aggregated views (`team_debrief_summary`, `student_contribution_summary`), and PL/pgSQL retention functions were validated against a live PostgreSQL instance—catching and fixing a multi-table join fan-out bug (`DBD §10`, `§14.4`). Similarly, all core backend state machines and algorithms were validated under `tsc --noEmit` with `strict: true` and `experimentalDecorators: true` (`TDD §11.1`).
3. **Elimination of the Cost-vs-Security Tradeoff:** By combining Docker Compose, self-hosted PostgreSQL/Valkey, and a narrow-privilege `sandbox-orchestrator` driving `runsc` (or E2B's free tier), SimOffice achieves kernel-isolated, tamper-resistant code execution at **$0–$10/month** instead of the $400–$1,300/month required by managed cloud Kubernetes stacks (`TSSD §7`).

### 7.6.2 Discussion of Design Trade-offs
* **Injection-Over-Mount Latency vs. Security (`TDD §6.1`):** Launching a second ephemeral container/session for each verification run adds a few hundred milliseconds of startup overhead compared to executing inside the student's running container. However, this trade-off is essential: sharing a container handle or mounting the harness into `/workspace` would allow students to inspect or tamper with the grading check (`PRD §8.5`).
* **Sequential vs. Parallel Check Execution (`TDD §3.4`):** Formal verification checks for a team run sequentially rather than in parallel so that multiple checks do not compete against the same `ResourceLimits` ceiling (`1 vCPU / 512 MB`) and trigger false-positive `resource_limit_exceeded` outcomes. Streaming each check's result over Colyseus as soon as it finishes preserves immediate user feedback.

## A.1 Prerequisites

```bash
# 3. Configure required secrets in .env (never commit .env to Git)
```

```sql
-- RETENTION & ANONYMIZATION FUNCTIONS (DBD §8)
CREATE OR REPLACE FUNCTION anonymize_expired_contribution_events(retention_days INT DEFAULT 180)
RETURNS INT AS $$
DECLARE affected INT;
BEGIN
    UPDATE contribution_events
       SET roster_entry_id = NULL
     WHERE roster_entry_id IS NOT NULL
       AND occurred_at < now() - make_interval(days => retention_days);
    GET DIAGNOSTICS affected = ROW_COUNT;
    RETURN affected;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE FUNCTION anonymize_roster_entry(target_roster_entry_id UUID)
RETURNS VOID AS $$
BEGIN
    UPDATE roster_entries
       SET display_name = 'Deleted Student',
           roster_passcode_hash = 'invalidated',
           is_anonymized = true,
           anonymized_at = now()
     WHERE id = target_roster_entry_id;
    UPDATE contribution_events SET roster_entry_id = NULL WHERE roster_entry_id = target_roster_entry_id;
    UPDATE verification_runs SET triggered_by_roster_entry_id = NULL WHERE triggered_by_roster_entry_id = target_roster_entry_id;
END;
$$ LANGUAGE plpgsql;
```

# APPENDIX C — TROUBLESHOOTING GUIDE

## C.1 Student Receives `409 ENVIRONMENT_NOT_READY` When Clicking a Workstation
* **Cause:** The session is still in the `created` (Lobby) or `provisioning` state (`API Spec §5.1`, `§7.1`). Students are allowed to enter the lobby, walk around, and chat as soon as the session is created, but workstations remain locked until the teacher starts the session.
* **Solution:** Instruct the teacher to click **Start Session** on `SCR-05` (`POST /api/v1/sessions/{sessionId}/start`) and wait for the status indicator to transition from `provisioning` to `active`.

## C.2 Student Receives `401 INVALID_ROSTER_PASSCODE` on Session Join
* **Cause:** The student entered a `rosterPasscode` (e.g., `WOLF-42`) that either contains a typo or belongs to a different `class_id` (`API Spec §3.2`).
* **Solution:** Verify the passcode spelling. If the student has permanently lost their passcode, they should leave the **Roster Passcode** field **blank** on `SCR-06` to join as a fresh roster entry (`API Spec §3.2`).

## C.3 Student Receives `409 SESSION_ROSTER_FULL`
* **Cause:** A **new** student (omitting `rosterPasscode`) attempted to join a session whose distinct roster count has already reached `max_roster_size` (`API Spec §3.2`, `§14.5`).
* **Solution:** If the student was already in the session and got disconnected, they must enter their echoed `rosterPasscode`—returning students are exempt from the roster cap. Otherwise, the teacher can increase `maxRosterSize` if the session is still in `created` status (`PATCH /api/v1/sessions/{id}`).

## C.4 `502 PROVISIONING_FAILED` When Starting a Session (`GVisorProvider`)
* **Cause:** `sandbox-orchestrator` could not launch the `runsc` container after 1 automatic retry (`TDD §10`). Usually caused by `/var/run/docker.sock` permission issues or `runsc` not being registered in `/etc/docker/daemon.json`.
* **Solution:** Check `docker compose logs sandbox-orchestrator`. Verify `docker run --runtime=runsc hello-world` succeeds on the host.

## C.5 Colyseus Schema Compilation Fails with TypeScript Decorator Errors
* **Cause:** `@colyseus/schema`'s `@type()` decorators require legacy TypeScript experimental decorators (`TDD §11 item 1`).
* **Solution:** Ensure `"experimentalDecorators": true` and `"emitDecoratorMetadata": true` are enabled in `server/tsconfig.json`.

## C.6 3D Building Exterior (`SCR-00`) Fails to Render on Old Lab PC
* **Cause:** WebGL is disabled in the browser or unsupported by the GPU driver (`PRD §10.4`, `TDD §9.1`).
* **Solution:** SimOffice automatically falls back to `WebGL-unavailable` mode (`webglUnavailable: true` in Zustand), rendering a static building image and a 2D access card. To restore full 3D, enable **"Use graphics acceleration when available"** in Chrome Settings (`chrome://settings/system`).

# APPENDIX D — REST API & WEBSOCKET ENDPOINT REFERENCE

All REST endpoints are prefixed with `/api/v1` (`API Spec v1.1`):

* **`POST /auth/login`** — Authenticates a Teacher (`email`, `password`) and returns a long-lived HS256 JWT (`role: "teacher"`). Rate-limited to 5 req/min/IP.
* **`POST /sessions/join`** — Authenticates/registers a Student (`joinCode`, `displayName`, optional `rosterPasscode`). Returns `200` (returning) or `201` (new) with `rosterEntryId`, `rosterPasscode` (`WOLF-42`), `appearance` JSONB, short-lived `token`, and `wsRoomUrl`. Rate-limited to 10 req/min/IP.
* **`DELETE /classes/{classId}/roster/{rosterEntryId}`** — Anonymizes a student's `roster_entries` row in-place (`anonymize_roster_entry`) and strips attribution across history tables.
* **`POST /classes` | `GET /classes` | `PATCH /classes/{classId}` | `GET /classes/{classId}/roster` | `GET /classes/{classId}/sessions`** — Teacher class and roster management endpoints.
* **`POST /sessions` | `PATCH /sessions/{sessionId}` | `POST /sessions/{sessionId}/clone` | `POST /sessions/{sessionId}/start` | `GET /sessions/{sessionId}` | `POST /sessions/{sessionId}/announcements` | `POST /sessions/{sessionId}/end`** — Complete session lifecycle, no-repeat variant selection, provisioning, live announcement broadcast, and unconditional teardown endpoints.
* **`GET /scenarios` | `GET /scenarios/{scenarioId}`** — Content library browsing endpoints filtered by `domain`, `departmentalShape`, and `difficulty`.
* **`GET /teams/{teamId}/workstation/files` | `GET .../files/{path}` | `PUT .../files/{path}` | `POST .../run-check` | `POST .../submit-verification`** — Team-scoped workstation file operations, debounced auto-save checkpoints, informal checks, and tamper-resistant ephemeral verification runs.
* **`GET /sessions/{sessionId}/dashboard` | `POST /sessions/{sessionId}/teams/{teamId}/hint`** — Teacher live monitoring (combining DB views + in-memory Colyseus state) and targeted hint delivery.
* **`GET /sessions/{sessionId}/debrief` | `POST /sessions/{sessionId}/teams/{teamId}/reveal-fix` | `GET /sessions/{sessionId}/debrief/me`** — Post-session teacher summary, teacher-triggered root-cause reveal, and student `"me"`-scoped personal contribution summary.
* **`PATCH /roster-entries/{rosterEntryId}/character`** — Persists student character `appearance` JSONB across sessions.
* **Colyseus WebSocket Room (`team-${teamId}`):** Client methods: `move`, `sitAtDesk`, `standUp`, `sendChat`, `sendPing`, `useEmote`. Server broadcasts: `verificationResult`, `environmentError`, `announcementPosted`, `hintReceived`, `sessionEnded`.

# APPENDIX F — GLOSSARY OF TECHNICAL TERMS

* **Diegetic UI:** User interface elements that exist within the fictional 3D game world (such as wall-mounted notice boards or desk monitors) rather than disconnected browser popups (`PRD §16.1`, `SAD §12`).
* **Ephemeral Verification Context:** A brand-new, short-lived container (`runsc`) or microVM session (`E2B`) created solely for the duration of a single `runVerification` call and destroyed immediately afterward in a `try/finally` block (`SSD §3.4`, `TDD §6`).
* **Fix Attribution:** The retrospective read-time algorithm (`computeFixAttribution`, `TDD §3.5`) that correlates `code_edit_saved` timestamps against a passing `verification_runs` timestamp to attribute root-cause resolution.
* **Injection-Over-Mount:** SimOffice's core security principle where the grading test harness is never mounted in the student-writable `/workspace` directory, but is injected transiently by the server into a separate execution context against a snapshot of the student's code (`SAD §7.2`, `SSD §3.1`).
* **Production Seam:** An intentional architectural boundary designed so that a lightweight single-college pilot component (e.g., Docker Compose, self-rolled JWT, `GVisorProvider`) can be upgraded to a multi-institution production service (GKE Kubernetes, Auth0, Cloud SQL) without rewriting application logic (`TSSD §9`, `SAD §17`).
* **Resource Ceiling:** Hard CPU (`1 vCPU`), memory (`512 MB`), and wall-clock (`30s`) limits enforced on every student sandbox so runaway loops or fork bombs cannot starve shared host infrastructure (`PRD §8.6`, `SSD §4`).
* **Roster Entry (`roster_entries`):** A persistent, class-scoped, credential-free student identity authenticated via a short human-friendly passcode (`WOLF-42`) that preserves avatar appearance and session history across a semester without collecting student PII (`DBD §3.1`, `§3.5`).
* **`runsc` (gVisor):** Google's open-source container runtime that implements an application kernel in user space, intercepting guest system calls to provide VM-grade kernel isolation without full hardware virtualization overhead (`SSD §17`).
